7. СИНХРОНИЗАЦИЯ
==================================================

Realtime до миллисекунд НЕ требуется.

Для семьи достаточно разумной eventual consistency.

Синхронизацию предусмотреть:

- при запуске;
- при возвращении приложения на экран;
- после локального изменения;
- после восстановления соединения;
- периодически, пока приложение активно.

Не делать агрессивный polling.

Интервал должен быть разумным и настраиваемым на уровне реализации.

Нужно учитывать конкурентное изменение двумя телефонами.

Пример:

Honor получил версию A.
iPhone получил версию A.

Honor добавил молоко → появилась версия B.

iPhone на основе A добавил хлеб.

Результатом НЕ должна становиться потеря молока.

Использовать:
- version/SHA/revision;
- optimistic concurrency;
- повторное получение актуального состояния;
- merge;
- retry;
- идентификаторы записей;
- timestamps.

Простая модель конфликтов допустима, но изменения с разных устройств не должны молча уничтожать друг друга.

Предусмотреть уникальный ID каждой сущности.

11. УВЕДОМЛЕНИЯ И WEB PUSH
==================================================

Web Push является предпочтительным основным механизмом уведомлений Family Hub.

Целевой пользовательский сценарий:

- Family Hub установлен на Home Screen iPhone как PWA;
- Family Hub установлен как PWA на Android;
- окно приложения может быть полностью закрыто;
- браузер не должен постоянно находиться на экране;
- телефон может быть заблокирован;
- при событии пользователь должен получить обычное системное push-уведомление, если ОС, браузер и выданные разрешения это позволяют.

Не использовать setTimeout/setInterval как механизм долгосрочных уведомлений.

Не рассчитывать на постоянно работающий JavaScript или постоянно открытую PWA.

Использовать стандартную архитектуру Web Push:

PWA
→ Service Worker
→ Push API / Push Subscription
→ внешний push sender
→ стандартная Web Push infrastructure браузера/ОС
→ Service Worker
→ системное notification.

Исследовать поддержку Web Push:

1. iPhone 16 / актуальная iOS / PWA, установленная через Safari на Home Screen.
2. Honor Magic 8 Pro / актуальный Android / PWA.
3. Приложение открыто.
4. Приложение закрыто.
5. Экран телефона заблокирован.
6. После перезагрузки телефона.
7. После обновления PWA/Service Worker.

Запрашивать Notification Permission только после явного действия пользователя и понятного объяснения назначения уведомлений.

Не показывать системный запрос разрешения автоматически при первом открытии.

Предусмотреть диагностический экран:

- standalone/PWA status;
- Service Worker registered;
- Notification API support;
- Notification permission;
- Push API support;
- push subscription status;
- subscription creation date;
- last successful push;
- last push error;
- кнопка «Отправить тестовое уведомление», когда backend для этого станет доступен.

Push subscription каждого устройства должна храниться безопасно.

Одному пользователю может соответствовать несколько устройств/subscriptions.

Предусмотреть удаление/обновление недействительных subscriptions.

Не отправлять пользователю push на устройство, инициировавшее изменение, если это не требуется настройками.

Примеры оперативных уведомлений:

«В покупки добавлено: Молоко»
«Добавлено 3 новых покупки»
«Вам назначено дело: заменить фильтр»

Избегать notification spam.

Несколько близких событий по возможности агрегировать:

НЕ:
«Добавлено молоко»
«Добавлен хлеб»
«Добавлен сыр»

ПРЕДПОЧТИТЕЛЬНО:
«В список покупок добавлено 3 позиции».

Для долгосрочных событий:

«Через 30 дней заканчивается срок действия паспорта»
«Через 7 дней — плановое ТО»
«Завтра день рождения»

требуется внешний scheduler/trigger, поскольку закрытая PWA не может надежно сама запланировать выполнение JavaScript через месяцы.

На этапе исследования уведомлений определить минимальный полностью бесплатный способ реализации:

scheduler
+
Web Push sender.

Требования к такому компоненту:

- нулевая стоимость для нашего масштаба;
- крайне малая нагрузка;
- отсутствие необходимости постоянно держать домашний компьютер или Android-телефон включенным;
- работа для пользователей в России без VPN;
- отсутствие платного API;
- отсутствие AI API;
- предпочтительно отсутствие требования банковской карты;
- возможность заменить компонент в будущем;
- никакого хранения лишних семейных данных.

Если для Web Push нужен минимальный serverless/backend component, это допустимый кандидат, но НЕ подключай конкретный внешний сервис без предварительного объяснения и моего подтверждения.

Раздел 4. GITHUB И ХРАНЕНИЕ ДАННЫХ:
ВАЖНО ПО АВТОРИЗАЦИИ В GITHUB:
Мы не используем платный бэкенд. Авторизация PWA в GitHub API для чтения/записи семейного приватного репозитория реализуется через механизм User-Provided Fine-grained Personal Access Token (PAT):

В бандле и исходном коде репозитория НЕТ никаких токенов.
Пользователь один раз генерирует PAT в своём GitHub-аккаунте (с ограничением прав только на репозиторий данных) и вставляет его в поле на экране «Настройки».
Токен сохраняется исключительно локально в IndexedDB конкретного браузера.
Все сетевые вызовы к GitHub API осуществляются напрямую из браузера с использованием сохранённого локально токена.


Раздел 11. УВЕДОМЛЕНИЯ И WEB PUSH:
Для отправки Web Push без финансовых затрат и без собственного 24/7 сервера использовать гибридный подход:

Долгосрочные напоминания (Сроки, Дни рождения): Реализуются через GitHub Actions Scheduled Workflow (Cron). Раз в сутки бесплатный Workflow считывает JSON сроков, формирует Web Push и отправляет их через VAPID-ключи на зарегистрированные endpoints подписок.
VAPID-ключи: Генерируются бесплатно один раз. Публичный ключ хранится в приложении, приватный — в GitHub Actions Secrets.
Резерв: Обязательная генерация стандартного .ics файла (календарного события) для добавления критичных дат в нативный календарь iOS/Android.
