## 1. СУТЬ ПРОЕКТА

Family Hub — приватное offline-first PWA для **одной семьи из 2–4 человек**.
Не коммерческий SaaS. Не нужны: тарифы, платежи, публичная регистрация, организации,
маркетинговые страницы, корпоративные роли.

**Направления:** Главная · Покупки · Дела · Сроки · Настройки.

**Целевые устройства (реальные, на них тестируем):**

- iPhone 16 (Safari → «На экран Домой»);
- Honor Magic 8 Pro (Android, Chrome/системный Chromium);
- другие современные мобильные браузеры — по остаточному принципу.

**Жёсткие ограничения (не обсуждаются):**

- 0 рублей для разработчика и для пользователей;
- никаких платных API, никаких AI API (OpenAI/Gemini/ChatGPT и т.п.);
- никаких SMS-сервисов и обязательных подписок;
- минимум внешних зависимостей;
- никаких секретов в коде, бандле, логах, коммитах и публичных файлах.

## 2. СОГЛАСОВАННЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 2.1. Репозитории и хостинг

**Решение владельца:** используем только GitHub. Cloudflare отклонён; новый
внешний бесплатный сервис — только после объяснения и явного одобрения.

| Репозиторий         | Видимость   | Содержимое                                                                        |
| ------------------- | ----------- | --------------------------------------------------------------------------------- |
| `FAMILY-HUB` (этот) | **public**  | код PWA, CI, шаблоны push-воркфлоу, документация. **Ни одного секрета.**          |
| `family-hub-data`   | **private** | семейные JSON, push-подписки и маркеры отправки; **никаких workflows** |

**Причина публичности репо кода:** GitHub Pages на тарифе Free публикуется **только из
публичных репозиториев**; приватный репо требует Pro/Team (платно) — см.
`docs/RESEARCH.md`, факт F1. Публичность кода приемлема: секретов там нет, токен
вводится пользователем в рантайме и хранится только в IndexedDB его устройства.

**Хостинг:** GitHub Pages (HTTPS из коробки, `https://<user>.github.io/FAMILY-HUB/`).

**⚠️ Cloudflare Pages как Plan B — ОТКЛОНЁН (проверено 2026-10-01).**
Первоначально предполагался как запасной хостинг. Проверка показала, что он **ухудшил бы**
ситуацию, а не улучшил: `*.pages.dev` внесен в реестр запрещённых ресурсов РФ **с мая 2024
года**, а значительная часть IP-адресов Cloudflare — с июня 2025 (факты F19–F21 в
`docs/RESEARCH.md`). Подробный разбор — `docs/RESEARCH.md`, раздел G.

**Важное различие, которое нельзя путать.** Существует **два независимых** внешних канала,
и их доступность не связана:

| Канал                      | Что это                                             | Чем рискуем                                                                           | Cloudflare помог бы?                                    |
| -------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **A. Оболочка приложения** | статические файлы `dist/` на `*.github.io`          | нельзя установить PWA на **новое** устройство и нельзя получить **обновление** версии | да, но `pages.dev` заблокирован → нет                   |
| **B. Данные семьи**        | `api.github.com` ↔ приватный репо `family-hub-data` | не работает синхронизация между устройствами                                          | **нет вообще** — Cloudflare к этому каналу не относится |

Канал A — **наименее опасный**: установленная PWA запускается из кэша Service Worker
бесконечно долго без всякого хостинга. Хостинг нужен только для первой установки и для
обновлений. Канал B — вот настоящий риск, и его Cloudflare не закрывает ни в каком виде.

**Поэтому фактическая стратегия устойчивости (вместо ложного Plan B):**

1. **Offline-first** — приложение полностью работает без канала B сколь угодно долго;
   изменения копятся в очереди.
2. **Агрессивный кэш app shell** — канал A может пропасть, а установленные устройства
   продолжают работать.
3. **Переносимость сборки** — `dist/` не зависит от хоста: `BASE_PATH` в одной переменной
   окружения, `HashRouter` (не требует серверного SPA-fallback), origin из `location.origin`,
   CSP генерируется из одного источника. Если появится доступный в РФ хостинг — переезд
   займёт минуты. Закладываем сразу, чтобы не переписывать потом.
4. **Автоэкспорт данных на устройство** — приложение периодически предлагает/делает
   локальную JSON-копию, которая остаётся у семьи даже при полной недоступности GitHub.
5. **Абстракция хранилища** (`RemoteAdapter`) — если появится проверенная альтернатива
   каналу B, добавляем один адаптер, не переписывая приложение.
6. **Честное признание:** на сегодня **не существует** проверенной бесплатной, доступной
   в России, CORS-совместимой замены GitHub для канала B. WebDAV (Яндекс Диск,
   Облако Mail.ru) бесплатен и доступен в РФ, но CORS для браузерных запросов **не
   подтверждён** (факт F22) — а без CORS PWA не сможет туда писать напрямую.
   План Б по данным не выдуман, а отложен до появления проверенного варианта.

### 2.2. Хранилище и синхронизация

```
UI (React)
  ↓  useLiveQuery (реактивные запросы к локальной БД)
application / service layer        ← вся доменная логика, merge, дедупликация
  ↓
repository layer (интерфейсы)      ← UI не знает, откуда данные
  ↓
├── LocalAdapter  → IndexedDB (Dexie)      — источник истины ДЛЯ ЭКРАНА
└── RemoteAdapter → GitHub Contents API    — источник истины ДЛЯ СЕМЬИ
```

**Принцип:** IndexedDB — кэш и очередь; **GitHub — источник истины**. Потеря локальных
данных на устройстве (очистка данных сайта, переустановка iOS) восстанавливается одной
загрузкой из GitHub. Это же — страховка от политики Safari по очистке хранилища
(факт F6).

**Авторизация:** User-Provided Fine-Grained Personal Access Token (PAT).

- В бандле и в репозитории токенов **нет**.
- Пользователь один раз генерирует PAT с правами **только** на `family-hub-data`
  (Contents: read & write) и вставляет в Настройках.
- Токен хранится только локально в IndexedDB конкретного браузера.
- Все вызовы идут напрямую из браузера в `api.github.com`.
- **CORS проверен фактически:** `api.github.com` отдаёт `access-control-allow-origin: *`
  (факт F4) → прокси не нужен.
- Лимит: 5000 запросов/час на пользователя (проверено фактически, факт F4).

**Усиление безопасности (обязательно, не опционально):**

```
default-src 'self';
script-src 'self';
connect-src 'self' https://api.github.com;
img-src 'self' data: blob:;
style-src 'self' 'unsafe-inline';
object-src 'none'; base-uri 'self'; frame-ancestors 'none';
```

Даже при внедрении чужого кода токен физически невозможно отправить на сторонний домен.
Никаких сторонних скриптов, шрифтов с CDN, аналитики и SDK.

**Конкурентный доступ (два телефона).** Обязательный сценарий из ТЗ: Honor добавил
молоко (версия B), iPhone на основе версии A добавил хлеб → молоко **не должно** потеряться.

Механика:

1. Каждая сущность: `id`, `rev`, `createdAt`, `updatedAt`, `updatedBy`, `deletedAt?` + доменные поля.
2. Каждый файл: `{ schemaVersion, fileRev, entities: { <id>: {...} } }`.
3. Запись: `GET contents/data/<file>.json` → запомнить `sha` и `fileRev` → **entity-level
   merge** локальной очереди поверх удалённого состояния (LWW по `updatedAt`,
   детерминированный tie-break по `updatedBy`+`id`) → `PUT` с `sha`.
4. `409 Conflict` → повторный `GET` → повторный merge → retry (макс. 3, экспоненциальный backoff).
5. **Tombstones:** удаление = установка `deletedAt`, а не физическое удаление.
   Без этого удалённая позиция воскресает при следующем merge. Компакция — через 30 дней.
6. **Неразрешимый конфликт** (обе правили одну сущность после общей базы): побеждает LWW,
   проигравшая версия пишется в `state/unresolved.json` и видна в Диагностике.
   **Модальных окон «выберите чья версия» не строим** (решение о сокращении, §3).

**Дебаунс записи:** не чаще одного коммита в 30–60 секунд на устройство + обязательный
flush на `visibilitychange:hidden` / `pagehide`. Это защита и от abuse-лимитов GitHub,
и от расхода минут Actions (§2.4).

**Чтение:** на старте, при `visibilitychange:visible`, при `online`, после локального
изменения, и периодически в foreground (по умолчанию 60 с, настраивается в коде).
Использовать условные запросы `If-None-Match` + ETag: ответ `304` не расходует лимит
(проверить в ЭТАПЕ 2 эмпирически). Агрессивного polling нет.

**Состояния синхронизации (обязательны в UI):** `online` · `offline` · `syncing` ·
`synced` · `sync error` + «последняя успешная» + «есть неотправленные изменения» +
кнопка «Синхронизировать сейчас».

### 2.3. Структура удалённых данных (репозиторий `family-hub-data`)

```
data/
  meta.json              # schemaVersion, familyId, lastSeenByDevice
  members.json           # профили: имя, аватар/цвет, deviceId
  shopping.json          # активные позиции + tombstones
  shopping-history.json  # купленное (лимит 500, ротация в archive/)
  tasks.json             # дела
  deadlines.json         # сроки
  dictionary.json        # canonical-товары, алиасы, выученные категории
  devices.json           # push-подписки устройств (endpoint, p256dh, auth, platform)
  settings.json          # ОБЩИЕ настройки: уведомления по модулям, тихие часы
  activity.json          # «Семейная лента», последние ~50 событий
state/
  notified.json          # идемпотентность отправителя push (что уже уведомлено)
  unresolved.json        # неразрешённые конфликты (для Диагностики)
archive/
  shopping-YYYY.json     # ротация истории
```

Отправитель находится **только в публичном FAMILY-HUB**:

```
.github/workflows/push-sender.yml  # cron */30 + ручной запуск
scripts/push-sender.mjs           # web-push, секреты только в Actions
scripts/push-sender-data.mjs      # адаптер RemoteFile.entities, тесты на фикстурах
```

Актуальные пути данных (включая `data/push/` и `data/push-sent/`) — в HANDOFF §1;
остальные файлы в дереве выше относятся к целевой модели.

**Персональные vs общие настройки.** Тема, компактность списка, группировка — **локально**
в IndexedDB, в общий файл не уходят. Тихие часы и включённость уведомлений по модулям —
в `settings.json`, потому что их обязан читать воркфлоу отправки push.

**Рост данных.** История покупок ограничена 500 позициями с ротацией в `archive/`.
Git-история репо данных растёт, но объём ничтожен (десятки КБ на коммит);
при необходимости — ежегодная orphan-ветка для архива (низкий приоритет).

### 2.4. Уведомления — канальная архитектура (РЕШЕНИЕ ВЛАДЕЛЬЦА)

Владелец попросил: начать с простого, заложить быстрое подключение другого решения,
переключение — одним тумблером в Настройках; рассмотреть вариант «уведомления только
при включённом экране».

**Честный ответ на этот вопрос.** «Только при включённом экране» — это не упрощение
Web Push, а **отдельный бесплатный канал**, который мы получаем в любом случае.
Вся сложность и весь российский риск сосредоточены ровно в одном месте: доставка
при закрытом приложении и заблокированном телефоне. Поэтому разбиваем на уровни.

**Единый интерфейс канала** (реализуется в ЭТАПЕ 1 как скелет, наполняется в ЭТАПЕ 3):

```ts
type ChannelId = 'local-foreground' | 'ics-calendar' | 'web-push';

interface NotificationChannel {
  readonly id: ChannelId;
  readonly label: string;
  readonly worksScreenOff: boolean; // честный флаг для UI
  readonly needsExternalInfra: boolean;
  isSupported(): Promise<SupportReport>; // что доступно на этом устройстве
  enable(ctx: EnableContext): Promise<EnableResult>; // разрешения, подписка
  disable(): Promise<void>;
  deliver(events: FamilyEvent[]): Promise<DeliveryReport>;
  diagnose(): Promise<DiagnosticSnapshot>; // для экрана «Диагностика»
}
```

Реестр каналов + один тумблер в Настройках. Каждый канал включается независимо.
Все каналы пишут в единый `NotificationLog` → экран «Диагностика» показывает,
**что реально дошло**, а не «что должно было».

**Правило по дефекту 2026-10-02 (0.3.6):** переключатель не инициализировать
по номеру уровня. Push восстанавливать по `diagnose().details.subscribed`
(подписка браузера), кэшировать в локальном kv `notify.channels.push` для UI
без мигания. Ошибка проверки не означает отсутствие подписки; запоздалая
диагностика не отменяет ручной выбор. ICS — `notify.channels.ics`, «включено»
означает файл скачан из настроек или Сроков; импорт неизвестен, выключение
не удаляет события в системном календаре. Новые флаги не синхронизировать
между устройствами и не менять ради них семейные данные.


| Уровень | Канал                                                                                                                            | Экран выключен | Инфраструктура              | Риск                            |
| ------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------- | --------------------------- | ------------------------------- |
| **0**   | `local-foreground` — лента на Главной + `registration.showNotification()` локально, пока приложение открыто или в фоне на экране | ❌             | **нет вообще**              | нулевой                         |
| **1**   | `ics-calendar` — критичные даты уходят в нативный календарь iOS/Android                                                          | ✅             | **нет вообще**              | нулевой                         |
| **2**   | `web-push` — GitHub Actions → Web Push                                                                                           | ✅             | VAPID в Secrets публичного FAMILY-HUB | **R2: FCM в РФ не подтверждён** |

**Уровни 0+1 закрывают бóльшую часть реальной потребности семьи без единого внешнего
риска.** Уровень 2 включается только после успешной проверки на обоих реальных
устройствах (ЭТАП 3 — жёсткий гейт).

**Канал `web-push` (Уровень 2) — как устроен.**

**Ревизия владельца 2026-10-01: только публичный отправитель.**

```
GitHub Actions в публичном FAMILY-HUB (main)
  ↓ schedule */30 или ручной Run workflow с выбором ветки
  ↓ через FAMILY_REPO_TOKEN читает сроки и подписки из приватного family-hub-data
  ↓ Web Push (VAPID_PRIVATE_KEY — только Secrets публичного FAMILY-HUB)
  ↓ пишет маркеры «уже отправлено» в data/push-sent/ приватного хранилища
```

Workflow в приватном репозитории данных **не запускать никогда**. Cron работает
только из default branch (main); ручной запуск допускает выбор текущей ветки,
поэтому исправления можно проверить без слияния. Статус `active` или зелёный
job сами по себе не доказывают доставку — см. открытые вопросы HANDOFF.

**Экономика:** публичные GitHub-hosted runners бесплатны без лимита минут
(проверенный факт F3). Cron раз в 30 минут не расходует 2000 минут приватного
репозитория; прежний расчёт «впритык» больше не используется.

**Ключевой принцип надёжности.** Воркфлоу **идемпотентен и state-driven**: каждый запуск
обрабатывает «всё, что ещё не было уведомлено» (сверяясь с `data/push-sent/`),
а не «события за последний интервал». Тогда пропущенный, задержанный или отменённый
запуск **не теряет уведомлений** — следующий догоняет. Это обязательное требование,
потому что GitHub документированно задерживает cron на 10–30+ минут и может молча
пропускать запуски (факт F2).

**Почему push НЕ отправляется напрямую с телефона.** Для отправки нужен **приватный**
VAPID-ключ. Положить его в браузер рядом с PAT = позволить любому слать семье
системные уведомления от имени приложения («Ваш аккаунт взломан, перейдите…»).
Это ровно та фиктивная защита, которую запрещает раздел 9 исходного ТЗ.
Поэтому: приватный VAPID-ключ живёт **только** в GitHub Actions Secrets публичного FAMILY-HUB.

**Declarative Web Push для iOS** (Safari 18.4+, только для web-приложений с Home Screen):
уведомление показывается **без пробуждения Service Worker** — заметно надёжнее на iOS,
где SW-слушатели могут не срабатывать после перезагрузки (факт F8). Chrome/Android не
поддерживает → там классический `push`-handler. Отправляем **один** payload с обеими
формами: `"web_push": 8030` + `notification{...}` для Safari, обычные поля для остальных.
Каждый браузер берёт своё.

**Правила отправки (анти-спам):**

- не отправлять push на устройство, инициировавшее изменение (кроме явной настройки);
- агрегировать близкие события: «В список покупок добавлено 3 позиции», а не три пуша;
- тихие часы (пер-пользователь, из `settings.json`);
- digest-режим «вечерняя сводка» как альтернатива мгновенным push по мелочам;
- iOS запрещает silent push: **каждое** сообщение обязано быть видимым, иначе iOS
  отзовёт подписку (факт F7);
- `410 Gone` / `404` от push-сервиса → подписка удаляется из `devices.json`.

**Разрешение на уведомления** запрашиваем только после явного действия пользователя и
понятного объяснения. Никакого автоматического системного запроса при первом открытии.

**Экран «Диагностика»** (обязателен): standalone/PWA status · Service Worker registered ·
Notification API support · Notification permission · Push API support · push subscription
status · дата создания подписки · последний успешный push · последняя ошибка push ·
активные каналы и их уровень · кнопка «Отправить тестовое уведомление» ·
расход минут Actions за месяц.

**Запрещено:** Telegram и любые мессенджеры как notification provider; схема
«Android-телефон будит iPhone»; `setTimeout`/`setInterval` как механизм долгосрочных
напоминаний; расчёт на постоянно работающий JavaScript.

### 2.5. Идентичность и подключение членов семьи

**РЕВИЗИЯ 2026-10-01 (по просьбе владельца, версия 0.1.3):** аккаунт GitHub создаёт
**только** тот, кто заводит семейное хранилище. Остальные члены семьи подключаются
**кодом подключения** (`src/data/remote/setupCode.ts`): одна строка
`FHSETUP1.<base64url>.<checksum>` содержит владелец/репозиторий/ветку/семейный ключ;
на втором устройстве — одно поле «вставить код». Аккаунт второму пользователю не нужен.
Прежняя формулировка «каждому свой PAT» оставлена как **опция для отзываемого доступа**
(выпустить отдельный токен и вставить вручную), а не как обязательный путь. Код
равносилен ключу, поэтому интерфейс предупреждает: передавать только внутри семьи.

**Честная модель (без иллюзий).** В приложении **нет логина**. Идентичность = локальный
профиль устройства (имя + цвет/аватар), заданный пользователем. `updatedBy` —
самодекларация. Любое устройство, владеющее PAT, может писать в репо данных.
Для семьи из 2–4 человек это приемлемо; для чего-либо большего — нет.
Это осознанное решение, а не недосмотр.

**Варианты авторизации, которые мы проверили:**

| Вариант                  | Автообновление                                           | Объём прав                            | Работает из браузера       | Вердикт                   |
| ------------------------ | -------------------------------------------------------- | ------------------------------------- | -------------------------- | ------------------------- |
| Fine-grained PAT         | ❌, истекает максимум через 1 год                        | ✅ только репо данных                 | ✅                         | **принимаем как базовый** |
| OAuth App + Device Flow  | ❌ (OAuth Apps не выдают refresh-токены)                 | ❌ scope `repo` = **все** репозитории | ⚠️ CORS не подтверждён     | отклонено                 |
| GitHub App + Device Flow | ✅ refresh без `client_secret`, токен 8 ч, refresh 6 мес | ✅ только установленные репо          | ⚠️ **CORS не подтверждён** | **спайк в ЭТАПЕ 2**       |

Про GitHub App + Device Flow — это прямой ответ на вопрос владельца «есть ли решение
безопасное, без лимитов по времени и бесплатное, которое обновляется в фоне».
**Теоретически да:** документация GitHub разрешает освежать user access token **без
`client_secret`**, если токен получен через device flow (факт F9). Это дало бы:
подключение в 3 тапа вместо генерации PAT, автообновление каждые 8 часов в фоне,
права строго на один репозиторий.

**Но я не смог это подтвердить экспериментально:** `POST https://github.com/login/device/code`
из среды разработки отвечает `404` и **не возвращает ни одного заголовка
`access-control-allow-origin`** (факт F10). Без CORS браузер не сможет завершить обмен
токена. Дополнительно: поддержка SPA у GitHub Apps — отдельная preview-функция, а
OAuth Apps для SPA не поддерживаются вовсе (факт F11).

**Поэтому:** не строим архитектуру на неподтверждённом. Базовый путь — fine-grained PAT.
В ЭТАПЕ 2 выделяем **30 минут** на спайк device flow в реальном браузере на реальном
GitHub App. Если CORS заработает — авторизация переключается одной настройкой, потому
что auth-слой спроектирован как стратегия (`AuthStrategy`), а не как хардкод PAT.
Если нет — остаётся PAT, и мы об этом просто сообщим.

**Смягчение главного недостатка PAT (истечение через год):**

- экран «Подключение» показывает оставшиеся дни;
- push-напоминание за 14 дней до истечения;
- при истечении приложение **не ломается**, а переходит в локальный режим с явным баннером;
- пошаговая инструкция по перевыпуску с точными ссылками на нужные экраны GitHub;
- **локальный режим без настройки вообще**: приложение полностью работает до ввода PAT.
  Это первый экран, а не аварийный. Сначала пользуешься — потом подключаешь синхронизацию.

**Онбординг нового устройства:** установить PWA → выбрать имя → (опционально) создать
репо данных по инструкции → вставить PAT → полная загрузка данных → подписка на
уведомления по выбранному уровню.

## 6. ОБЯЗАТЕЛЬНЫЕ ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ (из ТЗ, без изменений)

### 6.1. PWA

web app manifest · корректные иконки (192/512 + maskable + `apple-touch-icon`) ·
`display: standalone` · theme/background colors · Service Worker · кэш app shell ·
safe-area на iPhone (`viewport-fit=cover`, `env(safe-area-inset-*)`) ·
обработка `display-mode: standalone` · installability · update strategy для SW ·
понятное сообщение при появлении новой версии.
**PWA не должна быть функцией только Android. Особое внимание Safari/iOS.**
iOS: программного install-prompt нет → нужна иллюстрированная инструкция внутри
приложения + проверка standalone-режима.

### 6.2. Offline-first

последний список доступен без интернета · локальные изменения не пропадают ·
очередь offline-изменений · синхронизация после восстановления сети ·
видимое состояние синхронизации · ошибки синхронизации **никогда** не приводят к
молчаливой потере данных.

### 6.3. Покупки

ID · canonical product · отображаемое название · количество · единица измерения ·
категория · магазин (тег, опционально) · временной горизонт (Сейчас/Скоро/Когда-нибудь) ·
комментарий · кто добавил · время создания/изменения · статус выполнения · история.
Категории расширяемые. Магазин и категория — **разные** свойства.

### 6.4. Умный словарь без AI

`canonical item: milk` → `display: Молоко` → `aliases: молоко, молочка, пакет молока…`
Нормализация русского: lowercase · trim · `ё→е` · нормализация пробелов · очистка
пунктуации · распознавание чисел · распознавание единиц · алиасы · лёгкий стемминг.

⚠️ **Ограничение, которое надо учитывать (проверено логикой стемминга):**
стеммер Портера **не** объединит «молоко» → `молок` и «молочка» → `молочк`
(чередование к/ч стеммером не обрабатывается). Поэтому **алиасы остаются обязательным
механизмом**, а стемминг — лишь вспомогательным. Не обещать, что стеммер решает всё.

### 6.5. Семейный обучаемый словарь

Неизвестное («ватные диски») → пользователь выбирает категорию → приложение запоминает
для этой семьи → дальше классифицирует автоматически. Словарь редактируемый.

### 6.6. Дубликаты покупок

Есть «Молоко ×1», другой пользователь вводит «пакет молока 2» → система определяет тот же
canonical product. **Не объединять неоднозначные совпадения молча.**
Предложить: «Молоко уже есть в списке: 1. Добавить ещё 2?» → `Получится 3` /
`Добавить отдельно` / `Отмена`.

### 6.7. Быстрый ввод

«молоко 2, хлеб, бананы 2 кг, зубная паста» → разбиение на позиции.
Ввод через **системную диктовку клавиатуры телефона**. Собственный облачный
speech-to-text не создаём.

### 6.8. История и шаблоны покупок

Купленное не уничтожать навсегда. «Добавить снова» · часто покупаемое · шаблоны
(Еженедельная закупка, Дача, Поездка, Праздник). AI для предсказаний не используем.

### 6.9. Дела

**База 0.4.0 + уведомления 0.4.1 (03.10, приоритет изменён владельцем):** общий список/назначения/
необязательная date-only дата/выполнение/возврат/правка/tombstone, офлайн и общий
sync engine. План ниже — целевой, не обещание полной готовности. Уведомления реализованы по правилу владельца: только исполнителю — одно при назначении другим участником и одно в день срока; PBS и серверные push используют общий sender. Повторения и полная история пока не реализованы. Навигация/структура страниц прежние.

Название · описание · исполнитель · срок · статус · повторение · автор · история.
Повторение: ежедневно · еженедельно · ежемесячно · ежегодно · через N дней/месяцев
после выполнения.

### 6.10. Сроки

Документы · автомобиль · дом · страховка · обслуживание · дни рождения · произвольные даты.
Пример: `Тип: Документ` / `Паспорт Алексей` / `18.10.2030` / напоминания 90·30·7·0 дней.
Пример интервальный: `Фильтр воды` / `Заменён 15.10.2026` / `Период 3 месяца` →
«Заменён сегодня» автоматически считает следующую дату.
Различать: фиксированная дата · ежегодное событие · интервал после выполнения.
Для автомобиля архитектурно предусмотреть «по дате / по пробегу / что раньше»,
**но не реализовывать раньше соответствующего этапа**.

⚠️ **Семантика дат (критично, в ТЗ отсутствовала):** `18.10.2030` — календарная дата,
**не** timestamp. Хранить как `YYYY-MM-DD` (date-only). Все расчёты — в «локальных днях».
Хранение в epoch ms + переход на летнее время = напоминание, сдвинутое на сутки.

⚠️ **Рекурренция — определить правила явно:** 29 февраля · 31-е число в коротком месяце ·
«последний рабочий день». Подмножество RRULE, покрытое тестами.

⚠️ **Перекос часов устройства:** LWW-merge по `updatedAt` при неверных часах тихо теряет
данные. Авторитетное время — из timestamp коммита GitHub; для деструктивных изменений —
не тихий LWW, а фиксация в `state/unresolved.json`.

### 6.11. История сроков

Старый срок не исчезает при обновлении: `предыдущий 18.10.2030 → обновлён 03.10.2030 →
новый 18.10.2040`. История просматривается.

### 6.12. ICS / системный календарь

Формирование корректного ICS для долгосрочных сроков (Уровень 1 уведомлений).
**Не обещать двустороннюю фоновую синхронизацию с календарём** — browser API её не даёт.
Это канал доставки напоминаний, а не хранилище.

### 6.13. Настройки

Тема (системная/светлая/тёмная) · уведомления (общий переключатель + покупки/дела/сроки) ·
тихие часы · стандартные интервалы напоминаний · покупки (группировка, показ завершённых,
компактность) · синхронизация (статус, последняя успешная, неотправленные, кнопка Sync) ·
данные (Export/Import) · Диагностика.
Уровень уведомлений (§2.4) — отдельный тумблер.
Интерфейсные настройки — персональные (локально), уведомленческие — общие (`settings.json`).

### 6.14. Backup

Полный экспорт: `family-hub-backup-YYYY-MM-DD.json`, документированный формат.
Import с проверкой версии схемы, валидацией и **предупреждением до перезаписи/merge**.
Vendor lock-in минимальный. Опасные действия (удаление, сброс, импорт) — только через
подтверждение.

### 6.15. Дизайн

**Не делать:** Windows 95 · сайт начала 2000-х · desktop CRM, уменьшенную под телефон ·
мелкие элементы управления.
**Делать:** современный premium mobile UI 2025/2026, визуально близкий к iOS/macOS и
Material 3, без прямого копирования. Умеренно: cards · большие скругления ·
glass/translucent · backdrop blur · мягкие тени · layering · bottom sheets ·
floating actions · плавные переходы · micro animations · skeleton states · light/dark.
Glass умеренно. **Читаемость важнее декоративности.** Без blur — graceful degradation.
Progressive enhancement. Touch targets удобны пальцем.
Учитывать: safe areas iPhone · Home Indicator · Android navigation · экранную клавиатуру ·
portrait · разные размеры экранов. **Mobile-first**; desktop/tablet пригодны, но не главные.

### 6.16. Accessibility

Достаточный contrast · корректные labels · semantic HTML · keyboard accessibility ·
`prefers-reduced-motion` · screen-reader-friendly controls · touch targets ≥ 44px.
Доступностью ради эффектов не жертвуем.

### 6.17. Производительность

Быстрый запуск. Без огромных зависимостей, без ненужных UI-фреймворков, без загрузки
всего справочника/истории, без чрезмерного JS. Code splitting — если оправдано.
Не подключать библиотеку ради одной небольшой функции.

### 6.18. Качество кода

TS strict · нет `any` без причины · модульность · reusable components ·
separation of concerns · понятные имена · нет гигантских компонентов ·
error boundaries · централизованные domain types · schema validation для внешних и
импортируемых данных · `migrations`/`schemaVersion` для сохраняемых данных.
**Не overengineer: проект на 2–4 человека.**

### 6.19. Логирование

Не выводить чувствительные данные в production console. Безопасный лог синхронизации
допустим: `sync started` · `sync completed` · `conflict detected` · `retry`.
**Не** содержимое приватных сроков/покупок и **не** credentials.

### 6.20. Тестирование

Автоматические тесты для критичной логики: нормализация товаров · duplicate detection ·
merge/conflict resolution · date calculations · recurrence · import validation ·
push-sender (RFC 8291 + VAPID) на фикстурах.
**Не писать сотни бессмысленных тестов ради процента coverage.**
Manual checklist для iPhone 16 / Safari / Home Screen и Honor Magic 8 Pro / Chromium / PWA.

### 6.21. Приватность

Не храним: номера банковских карт · пароли · фото паспортов · сканы документов ·
полные реквизиты документов · медицинские документы.
Для напоминаний достаточно: «Паспорт Алексей», «Действует до 18.10.2030».
Серию и номер паспорта не храним.
Область видимости записи (семья / только пользователь) — в будущем, не усложнять раньше этапа.

### 6.22. Дисклеймер

Внутри приложения — короткий текст: данные справочные, приложение не заменяет специалиста
(актуально для напоминаний о документах, ТО, здоровье). Без обещаний «полного снятия
ответственности».

### Принцип сквозного скелета (добавлен 2026-10-01 по требованию владельца)

Владелец справедливо указал: «невозможность использовать синхронизацию и делиться

порядок этапов изменён: **существенный риск (синхронизация) проверяется первым**, а не

Правило для всех последующих этапов: каждая новая возможность доводится до состояния
«работает на двух реальных телефонах через синхронизацию», прежде чем переходить к
следующей. Красивый интерфейс без работающего обмена данными не считается прогрессом.

**Как проверяем на двух телефонах.** Канал проверки — **GitHub Pages с рабочей ветки**
(`deploy-preview.yml`): постоянный адрес `https://help-yourself-dvp.github.io/FAMILY-HUB/`,
обновляется на каждый push автоматически, установка на Home Screen — один раз. Так как
`api.github.com` отдаёт `access-control-allow-origin: *` (факт F4), PWA на этом адресе
обращается к GitHub напрямую: PAT, синхронизация и Service Worker работают.

**Live preview среды разработки (`*.e2b.app`) исключён из каналов проверки 2026-10-01:**
адрес живёт только пока открыта сессия, а в пределах живой сессии отдал владельцу
`Sandbox not found`. Требование владельца: канал проверки обязан быть постоянным и не
требовать повторной настройки после каждого обновления.

**Слияние в `main` не является условием публикации.** По регламенту merge в `main`

воркфлоу `deploy-pages.yml` (с `main`) и любые cron-воркфлоу остаются на ЭТАП 2+ и
запускаются только решением владельца.

**Главный протокол разработки (обязателен для любого ИИ в этом проекте):**

1. Выполняй **только текущий этап**. Не переходи к следующему самостоятельно.
2. После этапа: проверь сборку → запусти доступные автоматические проверки →
   запусти подходящий workflow → исправь ошибки → кратко перечисли созданное/изменённое →
   сообщи, что проверить вручную → **остановись**.
3. Следующий этап — только после явного подтверждения владельца.
4. Не имитируй выполнение тестов или команд. Невыполнимое в текущей среде — сообщай прямо.
5. Не удаляй рабочую функциональность предыдущих этапов без необходимости.
6. Перед серьёзным архитектурным изменением объясни причину.
7. Технически невозможное требование → не создавай фиктивную реализацию: сообщи об

### Приёмка 0.5.4 (2026-10-04)

Владелец: на Android верх экрана в порядке, на iPhone на каждой странице большая пустая
полоса до первой строки. Причина — безопасная зона сверху вычиталась дважды (`.app-shell`
и `.topbar`): на Android она равна нулю, на iPhone это ~120px. Исправлено: safe-area
считается один раз, верхние отступы экранов уменьшены (итого ~70px выигрыша). Сторож —
`tests/layout-top-space.test.ts`.

Отдельно зафиксировано решение владельца: **перенос в `main` — последний шаг работы**, после
завершения всех правок (нынешний сценарий: перенос закрывает доступ к репозиторию, потому
что проект считается завершённым). До этого автоматические push на iPhone не проверяются —
это финальный тест после переноса.
