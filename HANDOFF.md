## 2. ЧТО РАБОТАЕТ (проверено владельцем на устройствах)

- **Покупки**: общий список семьи; добавить/куплено/удалить/исправить (правка любым участником, попадает в ленту); категории (справочник семьи + чипы + автоподстановка категории прошлой покупки); массовый ввод «бананы 4 шт, хлеб, порошок» через запятую; количество/единицы из текста («2 кг»); горизонты (сегодня/неделя/месяц); группировка «по категориям» для магазина; «Повторить корзину»; «Часто покупают» (ввод в один тап).
- **Дела 0.4.1–0.4.2:** база из 0.4.0 + «Ближайшие дела» на Главной + уведомления только исполнителю (назначение другим и день срока, дедуп по трём каналам, метаданные assignmentId/assignedBy). Синхронизация данных подтверждена отчётом владельца (tasks.json PUT, pulled 41). Ждём приёмку на телефонах. Повторения и полная история дел по-прежнему не реализованы.
- **Сроки**: документы/машина/дом/страховка/подписка/ДР/прочее; ступени напоминаний 90/30/7/0 + **свои** (1–3650 дней, «за полгода/год»); **цветные правила**: пресеты по типу (документ жёлтый 365/красный 90, машина 30/14, дом 21/7, страховка 30/14, подписка 7/3, ДР 14/3, прочее 30/7) + ручная перезапись порогов у каждого срока (`src/domain/deadlineRules.ts`).
- **Синхронизация**: 3-way merge (tie-break updatedAt→updatedBy→id), tombstones, ETag/304, retry×3 с backoff на 409, debounce 2 с + flush на hidden/pagehide + периодическая 60 с, таймаут 20 с. Офлайн-работа: IndexedDB (Dexie) — источник правды, очередь отправки.
- **Уведомления** (политика владельца — §4, п.7):
  - Уровень 0, локально при открытом приложении — работает (напоминания о сроках + «здоровье»: ключ истёк, нет доступа, репо не найден, validation).

Срабатывание будильника, полная семейная выгрузка, Google и iPhone не подтверждены. Формат 2: обычные события 09:00–09:15 (Москва), VTIMEZONE/DTEND, UTF-8 folding, точные будильники. Google официальный путь — F24. `notify.channels.ics` всё ещё означает только скачивание, не импорт; тестовый файл не включает резерв семьи. Выключение не удаляет события календаря.
  - Уровень 2, **Web Push** — **отдельная проверка на Honor подтверждена владельцем после 0.3.8**, iPhone ещё не пробовали. Run workflow из ветки сессии (не main), 37004747933/success; это не приёмка автоматических напоминаний/cron. Протокол SW 2, счётчики/маршруты сохранены. 0.3.9: внешний вид icon/badge и повторная закрытая доставка на Honor **приняты владельцем 03.10**; iPhone всё ещё ждём. Chrome/Android могут сохранить системную атрибуцию/скрыть содержание, не обещать исчезновение Chrome. Подписки приватные, ключи не менялись.

## 5. СРЕДА РАЗРАБОТКИ — ГРАБЛИ (проверено на практике)

- **Sandbox сбрасывается СЛУЧАЙНО, в т.ч. между вызовами внутри хода** (6+ раз): незакоммиченные правки tracked-файлов теряются, untracked выживают. Рецепт восстановления: `npm ci --silent`; `git fetch origin`; `git reset --mixed origin/arena/01a0fbcb-family-hub`; файлы со статусом ` D` — `git checkout --`. **Коммитить сразу после green.** Перед повторным применением патча — grep-ом проверить, не применён ли он уже.
- Права бота `arena-ai-coding-agent[bot]`: push/pull в ветку сессии, чтение actions/runs/jobs/check-run annotations, создание PR. **403**: secrets, workflow_dispatch, POST pages, gist, merge в main (проверить по факту).
- `tsc` запускать только `./node_modules/.bin/tsc -b` (npm auto-picks TS7 — pin typescript@^5).
- Сборка: `BASE_PATH=/FAMILY-HUB/ npm run build`; после неё обновить `infra/pages-fallback/dist`.
- eslint строгий: no-floating-promises (`void`), no-useless-assignment (`let x: string | undefined`), setState синхронно в useEffect — только render-phase паттерн.
- TS 5.x typed arrays: `PushManager.subscribe({applicationServerKey})` требует `ArrayBuffer`, не `Uint8Array`.
- IndexedDB: `.equals(null)` НЕ работает — только toArray+фильтр (регресс-тест tests/no-null-keys.test.ts).
- Два sibling-элемента в `{cond && (...)}` = TS2657 — оборачивать в фрагмент/один корень.
- Python-батч патчей: assert падает на первом непрошедшем якоре → файл не записывается вовсе; якоря ломаются после prettier — перед патчем читать актуальный текст.
- push rejected → fetch+merge, никогда force-push.

## 18. ЗАПРЕТ НА «СВОИ» ЗАГОЛОВКИ В ЗАПРОСАХ К GITHUB (0.4.4)

- Регрессия 0.4.2–0.4.3: `Cache-Control: no-cache` в чтении файла ломал CORS-preflight,

  добавлять. Тест `tests/github-headers.test.ts` это стережёт — не удалять.
- Свежесть чтения (sha перед записью) — параметром URL `&_=<время>` при `fresh = true`

- Любую правку заголовков проверять preflight-запросом curl к api.github.com, а не
  догадками: браузер сообщает только «Failed to fetch», причины не раскрывает.

  (`replace`), и с регрессионным тестом на «перезагрузку» (unmount + новый render).
- Тест-сторож: `tests/compose-intent.test.tsx`. Он проверяет и то, что запрос гасится, и
  то, что перезагрузка не открывает форму в покупках, делах и сроках.

## 26. УВЕДОМЛЕНИЯ: ЧЕГО НЕ УМЕЕТ GITHUB И iPHONE (0.5.2, НЕ ЗАБЫВАТЬ)

- **Расписания GitHub — «по возможности»**: задержки 5–20+ минут под нагрузкой, иногда
  запуск пропадает совсем. Начало часа — худшее время; в рабочей ветке cron `17,47`.
- **Публичный репозиторий: расписание выключается после 60 дней без коммитов** (письмо
  примерно за 23 дня; включить обратно — кнопка в Actions). Для долгого горизонта
  («через год-два») — главный риск. Любая активность в репозитории продлевает жизнь.
- **Расписания выполняются ТОЛЬКО из ветки по умолчанию.** Значит, автоматические
  напоминания сейчас идут версией из `main` (старый отправитель, cron `*/30`, без дел), а
  улучшенный отправитель живёт в рабочей ветке и запускается только вручную. Чтобы
  автоматика работала новой логикой, нужен один коммит в `main` с файлом воркфлоу —
  решение за владельцем (спрошено 04.10.2026).
- **iPhone:** web push требует установки приложения на экран «Домой» (iOS 16.4+);
  вкладка Safari в фоне push не получает. Подписки iOS могут тихо умирать, и, в отличие
  от Chrome, iOS не всегда отвечает 410 — отправка выглядит успешной. Фоновой
  синхронизации на iOS нет: только push и догон при открытии приложения.
- Не обещать точное время напоминания «в 9:00»: реально это «первый запуск после 9:00»,
  то есть 9:17–9:50 плюс задержка GitHub.

## 31. ПОКУПКИ: ДАЙДЖЕСТ И РЕАЛЬНАЯ ЧАСТОТА РАСПИСАНИЙ (0.5.6, НЕ ЗАБЫВАТЬ)

- Тумблер «Push об изменениях корзины» до 0.5.6 **ничего не включал**: кода не было ни в
  приложении, ни у отправителя. Теперь согласие публикуется в `data/push/<устройство>.json`

- **Проверить дайджест можно вручную:** Actions → «Push reminders» → Run workflow → выбрать

  приложении» и тумблер покупок, с другого устройства добавить позицию. Результат цикла
  виден в аннотациях запуска («Покупки: подписок с дайджестом N, отправлено M, ошибок K»).
- Если отправлено > 0, а уведомление на устройстве не появилось — это уже отдельный дефект
  доставки (VAPID/подписка/система), и разбирать его надо по аннотациям запуска.

## 36. ЛЕНТА: ЧТО БЛОКИРОВАЛО, И ТОЧНЫЕ ШАГИ ДЛЯ ВЛАДЕЛЬЦА

Проверка владельца 05.10.2026 по 0.6.0 дала две находки — обе разобраны и закрыты в 0.6.1.

**1. «Не найден адрес публичного репозитория (vapid.json → feed)».** Причина: service worker
отдавал `vapid.json` из кэша по стратегии «сначала кэш, потом сеть». Исправлено: ветка для
`vapid.json` в `public/sw.js` берёт файл из сети (`cache: 'no-store'`), кэш — только когда
сети нет; читатели настроек (`feed.ts`, `wake.ts`, `channels.ts`) тоже просят копию мимо
кэша браузера. Сторож: `tests/sw-config-freshness.test.ts`.

**2. Право токена (fine-grained).** По официальной документации GitHub («Create a workflow
dispatch event») для запуска проверки нужно право **`Actions` (write)** — это отдельная
строка от того, что у владельца уже стоит («Read and Write access to actions and code»).
Кроме права, fine-grained-токену нужен доступ **к самому публичному репозиторию**: в
скриншоте владельца в Repository access указан только `family-hub-data`, а запускать надо
`Help-yourself-dvp/FAMILY-HUB`. Точные шаги:
  1. github.com → аватар → Settings → Developer settings → Personal access tokens →
     Fine-grained tokens → нужный токен → Edit.
  2. Repository access → добавить `Help-yourself-dvp/FAMILY-HUB` (можно «Only select
     repositories» с обоими репозиториями).
  3. Repository permissions → **Actions → Read and write** → Save. Значение токена НЕ
     меняется: в приложении заново вставлять ничего не нужно.
  4. Проверка: Настройки → Уведомления → «Проверить сейчас» — должно стать «Отправлено…».
Если права не давать — «будильник» не работает, но и не нужен: после переноса в main цикл
идёт каждые ~5 минут.

**3. Главная находка: расписание живёт в `main`.** GitHub запускает `schedule` только если
файл рабочего процесса есть в ветке по умолчанию, и берёт версию ИЗ НЕЁ. Пока `main` на
0.4.x/0.5.x, лента не публикуется вовсе, а cron остаётся `17,47`. Поэтому включение ленты
для семьи и частое расписание начнутся **после переноса в `main`** — это последний шаг,
слово владельца обязательно. При переносе не забыть: `pushWake.ref` в `public/vapid.json`
переключить на `main`, иначе «будильник» будет запускать версию рабочей ветки.

## 37. ЛЕНТА: ВКЛЮЧЕНИЕ ДО ПЕРЕНОСА В MAIN (быстрый путь для владельца)

Ветка `feed` в публичном репозитории **ещё не создана** — публиковать ленту не запускалось ни
разу (все запуски по расписанию идут из `main`, а в `main` прежний отправитель без ленты).
Проверено 05.10.2026: `gh api repos/.../branches` знает только `main` и две рабочие ветки.

**Самый быстрый способ увидеть ленту, не делая перенос:** GitHub → Actions → «Push reminders»
→ Run workflow → **ветка `arena/01a0fbcb-family-hub`**, режим `reminders`. Ручной запуск берёт
код из выбранной ветки, поэтому в нём уже есть публикация ленты. Запуск создаст ветку `feed`
и положит по ссылкам из `data/feed.json` два файла (`<slug>.ics`) — сроки и дела.

Проверка результата: открыть скопированную ссылку в браузере. Ожидаемо — текст, начинающийся
с `BEGIN:VCALENDAR` (это видны только названия и даты, секретов там нет). «404: Not Found» —
публикация ещё не прошла; посмотреть причину: Actions → Push reminders → аннотации запуска
(«Лента: …»). Google Calendar сам перечитывает подписку раз в несколько часов (до суток); чтобы
проверить сразу — удалить календарь из Google и добавить ссылку заново (при добавлении Google
скачивает файл сразу). На iPhone подписной календарь обновляется чаще.

**Токен (по снимку 05.10.2026).** В «Repository permissions» строка «Read and Write access to
actions and code» = право Actions уже есть; «Repository access» содержит только
`family-hub-data`. Нужно добавить `Help-yourself-dvp/FAMILY-HUB` в Repository access — значение
токена при этом не меняется. Приложение 0.6.2 после отказа 403 само скажет, чего не хватает.

**Устройства.** Ссылка одна на всю семью (лежит в `data/feed.json` семейного хранилища), поэтому
на втором телефоне её не нужно пересылать: достаточно открыть Настройки → Уведомления → Лента
и скопировать ту же ссылку; у разделов «Сроки» и «Дела с датой» адреса разные.

## 40. БЕЗ ПЕРЕНОСА В MAIN ПУБЛИКАЦИЯ ДЕРЖИТСЯ ТОЛЬКО НА «БУДИЛЬНИКЕ»

Живой случай 05.10.2026 (15:00 мск): владелец добавил событие, в Google его нет. Ветка `feed`
последний раз менялась в 14:48:30, новых запусков отправителя после 14:48:18 НЕТ. Значит,
правка не попала в публикацию — и это не Google.

Механика: до переноса в `main` расписание запускает СТАРЫЙ отправитель (без ленты), поэтому
лента обновляется только после просьбы «будильника». Просьба ограничена одной в минуту, и
раньше вторая правка в пределах минуты молча терялась. Исправлено в 0.6.5: приложение
планирует повтор, когда окно истечёт. Плюс в блоке ленты появились кнопки «Обновить ленту
сейчас» и «Перечитать файл».

Порядок для владельца, если событие не видно: (1) «Обновить ленту сейчас» → подождать 1–2
минуты → «Перечитать файл»; (2) в Google удалить календарь и добавить ссылку заново (Google
скачивает файл при добавлении; сам перечитывает часами); (3) если в сверке написано «личный
срок» или «без даты» — поправить саму запись.

Постоянное лекарство — перенос в `main`: тогда цикл идёт каждые ~5 минут и публикация перестаёт
зависеть от одной кнопки.
