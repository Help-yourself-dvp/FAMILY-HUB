Цель владельца: «не дёргать телефон лишним разом и не тратить бесплатные минуты
GitHub, которые рассчитаны впритык». Ниже — матрица событий и расчёт стоимости

## Матрица событий

| Событие                                                          | Где видно                        | Уведомление                                 | Почему                                 |
| ---------------------------------------------------------------- | -------------------------------- | ------------------------------------------- | -------------------------------------- |
| Семья добавила/купила/удалила, приложение ОТКРЫТО                | маркер статуса + семейная лента  | нет                                         | человек и так смотрит в экран          |
| То же, приложение ЗАКРЫТО                                        | лента после входа                | push уровня 1, **дайджестом**               | полезно, но не по писку на позицию     |
| Ошибка, требующая действия (ключ истёк, нет доступа к хранилищу) | плашка в приложении              | push уровня 0                               | молча данные не уедут — нужно действие |
| Приложение обновилось                                            | плашка «обновилось с версии X»   | нет                                         | обновление не требует решения          |
| Напоминание о сроке (ЭТАП 6)                                     | лента + маркер                   | push уровня 1, один раз в назначенное время | суть напоминаний                       |
| Смена профиля, технические события синхронизации                 | только диагностика               | никогда                                     | служба, не семья                       |
| Конфликт слияния, разрешённый автоматически                      | лента («требует внимания» позже) | нет, пока нет ручного разрешения            | ЭТАП 11                                |

Дайджест вместо писка: не более одного push на устройство в 30–60 минут,
текстом «Семья: 3 изменения в списке», без перечисления покупок (приватность и
спокойствие).

## Экономика минут GitHub Actions

- Приватный репозиторий (`family-hub-data`) на бесплатном тарифе ест общие
  2000 минут/месяц организации. Любой workflow в нём — расход.
- Публичный репозиторий (`FAMILY-HUB`) минуты не лимитирует вовсе.
- Вывод: отправитель push живёт ТОЛЬКО в публичном репозитории и читает данные
  через секретный ключ с правом чтения одного приватного репозитория. Платные
  минуты не расходуются независимо от частоты.
- Частота: cron раз в 30 минут = ~1440 запусков/месяц по 20–30 с ≈ 10–12 часов
  рантайма — всё в публичном репозитории, т.е. 0 платных минут. Дайджест
  означает, что устройствa получают ≤ 1 push за интервал, а не за каждое изменение.
- Устройство-инициатор (workflow_dispatch на каждое изменение) отвергнуто: шум и
  зависимость от того, открыто ли приложение у отправителя.
- Совсем без push (только локальные уведомления при открытом приложении) = 0
  минут и 0 новых механизмов: это вариант «минимум» на ближайшие этапы.

## РЕШЕНИЕ ВЛАДЕЛЬЦА (2026-10-01, приёмка 0.1.10) — действует вместо рекомендации

1. **Уведомления нужны в первую очередь для долгосрочных напоминаний**: истечение
   сроков документов, мероприятия и прочее (модуль «Сроки», ЭТАП 6).
2. **Push о покупках — отдельный переключатель в настройках, выключен по
   умолчанию**, мера «на всякий случай»: при наполнении корзины пуши были бы
   спамом. Реализован переключатель `notify.shoppingPush` (0.1.11); доставка
   включится на ЭТАПЕ 3 и только дайджестом (≤ 1 push / 30 минут).
3. **Уведомлять о действительно важных событиях, включая работоспособность
   приложения**: ключ истёк/отозван, нет доступа к хранилищу, репозиторий не
   найден, данные повреждены (healthWatch, 0.1.11, уровень 0 локально; push тем
   же правилом на ЭТАПЕ 3). **Потерю сети и таймауты НЕ уведомляем** — преходящее.
4. Push «на каждое событие» не делать никогда: шум, батарея, минус доверие.
5. Экономика минут не меняется: любой отправитель push живёт только в ПУБЛИЧном
   репозитории FAMILY-HUB (0 платных минут приватного family-hub-data).

В рабочей ветке теперь workflow_dispatch включает FH_PUSH_MODE=test:
- срок не создаётся, надо только заранее закрыть PWA/заблокировать телефон;
- Run workflow → обязательно рабочая ветка → второй Run;
- отдельный видимый «Family Hub: проверка push» на каждую активную подписку;
- каждый явный запуск — новый tag, TTL 300 с, high; это не дубль срока;
- только GET подписок, без чтения сроков/push-sent, без PUT/DELETE и без локального
  маркера срока; статистика Web Push всё равно подтверждает обработку на устройстве;
- нет конфигурации/подписок или сбой проверки — error/exit 1, не ложный green;
- annotations только числа/HTTP-коды. Accepted у провайдера не доказывает экран телефона.

Schedule выбирает reminders и сохраняет anti-spam. В main все изменения ещё
отсутствуют, branch selection необходим даже при правильной версии PWA. Прежний
тест «повтор manual workflow не должен дать дубль срока» больше не применим к
проверочному режиму; идемпотентность настоящего режима отдельно покрыта фикстурой.

Владелец подтвердил SW protocol=2, переход по уведомлению в Сроки и прямой

## ТОЧНАЯ ТЕКУЩАЯ СХЕМА — ДЛЯ ДРУГОГО ПРОЕКТА

1. **Откуда отправляем.** `.github/workflows/push-sender.yml` в публичном
   `Help-yourself-dvp/FAMILY-HUB`. Cron загружается GitHub только из default main;
   в нашей рабочей ветке подготовлены 17/47 минут (интервал 30), в main пока старый
   00/30 и код 0.3.5. Public workflow не расходует лимит минут private data repo.
2. **Где подписки.** В приватном `Help-yourself-dvp/family-hub-data`, ветка main,
   `data/push/<deviceId>.json`. `WebPushChannel.enable()` в channels.ts запрашивает
   разрешение по явному действию, получает `reg.pushManager.subscribe` с публичным
   VAPID, записывает `subscription: sub.toJSON()` через GitHub Contents API.
   JSON содержит deviceId/subscribedAt/revoked и subscription (endpoint,
   expirationTime, keys.p256dh/keys.auth). Значения НЕ публиковать/не логировать/
   не отдавать AI. Это динамические приватные файлы, **не Secrets**.
3. **Что в Secrets.** В публичном репо кода: FAMILY_REPO_TOKEN (доступ к одному
   data repo), VAPID_PRIVATE_KEY. Публичная половина — public/vapid.json.
   Для другого проекта отдельная пара VAPID/репо/ключи доступа; действующие ключи
   семьи не копировать. Private workflows никогда не нужны.
4. **Кто отправляет.** Node 24 в Actions, npm ci, scripts/push-sender.mjs,
   пакет web-push 3.6.7. В обычном режиме читает deadlines.json + subscriptions +
   private push-sent markers, вычисляет ступени, отправляет JSON с title/body/route/tag
   и VAPID. Manual из этой ветки — scripts/push-test.mjs, отдельная проверка без
   чтения сроков/маркеров и без изменений данных. Secrets передаются только процессу
   отправителя, не в публичный бандл.
5. **Что на телефоне.** HTTPS PWA + зарегистрированный public/sw.js:
   push → registration.showNotification → notificationclick → hash-раздел.
   Для iOS — iOS 16.4+, Safari → На экран Домой, запуск именно установленной PWA,
   явное разрешение и подписка. Постоянно открытый сайт/APK/APNs-сертификат не нужны
   (F7). Classic Service Worker Push сейчас, **Declarative web_push:8030 пока не
   добавлен** (F8 не равно реализованному коду). Телефон идёт через собственный
   push-сервис браузера/Apple; Actions лишь отправитель. Фон на iPhone этим проектом
   ещё не доказан, не обещать его по результату Honor.

Это схема небольшой доверенной семьи: участники получают доступ к одному
хранилищу. Она не является готовой безопасной моделью доступа для публичного
многопользовательского сервиса. Не запускать sender с секретами на непроверенном
чужом коде/PR, не сохранять в репозитории Secrets/endpoint/реальные подписки.

## КАЛЕНДАРНЫЙ БУДИЛЬНИК: КАК ПРОВЕРИТЬ И ЧТО ОЗНАЧАЕТ «ЗА НЕСКОЛЬКО МИНУТ»

- Владелец открыл импортированное событие и увидел напоминание «за несколько минут» —
  значит будильник при импорте **не потерялся**, просто он срабатывает раньше начала
  события (09:00) и его легко пропустить.
- В наших файлах: сроки — событие 09:00 и `VALARM` на каждую ступень (`TRIGGER:-P{N}D`,
  для «в день срока» — `PT0S`); проверочные файлы — 09:00 с `PT0S`.
- Кнопка **«Проверить будильник через 5 минут»** (Настройки → Уведомления) скачивает
  отдельный .ics: одно вымышленное событие через ~6 минут, `TRIGGER:-PT1M` (за минуту
  до начала), время в UTC — без неоднозначности часового пояса. Семейные сроки и
  календарный резерв не затрагиваются.
- Если этот файл даёт всплывающее уведомление — native VALARM на Honor работает,
  и вчерашний пропуск объясняется временем/режимом телефона.
- Если не даёт — сначала проверяем телефон, а не файл: разрешения календаря,
  «Не беспокоить», ограничения батареи/фона, показ на экране блокировки; сравнить с
  вручную созданным событием на то же время. Разные календари по-разному обрабатывают
  импортированные будильники — гарантировать поведение чужого приложения нельзя.
- Семейный .ics присылать не нужно: проверки идут на вымышленных событиях.

## РЕГРЕССИЯ 03.10.2026: «data/push/<device>.json does not match <sha>» ПРИ ВКЛЮЧЕНИИ PUSH

Что видел владелец: `GitHubError: data/push/dev-d6348569.json does not match 48d2b9…`
и совет «Web Push недоступен на этом устройстве … нужны сервисы Google»; повторный
вход в приложение и повторное включение сработали.

Разбор:

1. Это **GitHub 409**: файл успели изменить между нашим чтением ручки (sha) и записью.
   Кто мог: сам владелец (второй тап по тумблеру), второе устройство, автоматический
   отправитель напоминаний. Сбой не связан с сервисами Google и не делает устройство
   «неподдерживаемым».
2. **Ложный текст** давался фильтром «в сообщении есть push» — путь `data/push/…`
   подходил под фильтр. Теперь сбой хранилища классифицируется по коду GitHubError
   (конфликт / сеть / таймаут / лимит / права), и только настоящая ошибка push-службы
   (AbortError, «push service error», NotAllowedError) говорит про устройство.
3. **Лечение в 0.4.2:**
   - повтор записи со свежим sha (до 3 попыток, только при конфликте; 403/сеть — нет);
   - второй параллельный тап не запускает вторую запись (флаг `toggling`);
   - чтение Contents API идёт с `Cache-Control: no-cache` (защита от устаревшего sha
     из кэша);
   - если запись не удалась, состояние честное: «подписка создана, но не сохранена,
     повторите» — повтор безопасен, подписка уже в телефоне.
4. **Диагностика:** шаги `upload-conflict-N`, `upload-ok-retry-N`, `upload-aborted`.
   При жалобе на включение просить свежий отчёт: видно, гонка это, права или сеть.

## КАЛЕНДАРЬ 0.4.2: ПОЧЕМУ БЫЛИ ДУБЛИ И КАК ТЕПЕРЬ

- Поведение телефона: при импорте файла Android-календарь показывает **все** события
  файла и добавляет их одним действием; выбрать часть нельзя. Значит повторная выгрузка
  всей семьи = повторный импорт уже добавленного.
- **Кнопка с календарём в строке срока** — файл ровно с одним событием, с теми же
  будильниками (`VALARM`) и тем же `UID`, что и полная выгрузка: клиенты, сопоставляющие
  UID, обновят существующую запись.
- **«В календарь: только новое (N)»** — в файл попадают сроки без отметки выгрузки, а
  также изменившиеся (`rev` или дата). Отметки лежат в `notify.calendar.exported`
  на устройстве; «Сбросить отметки выгрузки» и «Полная выгрузка» — в Настройках.
- **Изменённый срок**: отметка снимается автоматически, событие попадает в файл снова;
  старую запись в календаре нужно удалить вручную — Android-календари UID-обновление не
  гарантируют. Об этом честно сказано в сводке после скачивания.
- **Дубли, которые уже накопились**, убираются один раз вручную: удалить события
  «[Срок] …» в календаре телефона. Дальше схема «только новое» их не создаёт.
- **Чего браузер не может:** записать событие в системный календарь без человека.
  Поэтому «добавить автоматически» невозможно; можно только подставить событие
  (файл .ics или ссылка Google) и попросить подтверждение.
- **Ссылка «Открыть в Google Календаре»** — форма создания события с заполненными
  полями; напоминания Google в такую ссылку не принимает, их задаёт настройка
  календаря. Основной путь — .ics: он несёт наши будильники (проверено владельцем
  03.10: сообщение пришло).

## 0.4.4: ПОЧЕМУ «Ошибка: network / Failed to fetch» — ЭТО БЫЛА НАША ОШИБКА

- `status: 0` и «Failed to fetch» означают, что браузер не получил ответа вовсе.
  У всех запросов сразу + маленькое `ms` + `online: true` = отклонённый CORS-preflight,
  а не отсутствие интернета.
- Причина 0.4.2–0.4.3: заголовок `Cache-Control: no-cache` в чтении файла. GitHub
  разрешает в preflight только Authorization, Content-Type, If-None-Match,
  X-GitHub-Api-Version и ещё несколько — `Cache-Control` в списке нет.
- Лечение: заголовок убран; свежесть чтения перед записью подписки — параметром URL
  `&_=<время>`; регрессию стережёт `tests/github-headers.test.ts`.
- Для push это же объясняет, почему включение канала могло «не сохраняться»: загрузка
  подписки в `data/push/<device>.json` тоже упиралась в отклонённые запросы.


## 0.4.5: КАЛЕНДАРЬ — ЧТО САЙТ МОЖЕТ И ЧЕГО НЕ МОЖЕТ (ПРОВЕРЕНО ПО ДОКУМЕНТАЦИИ)

Проверено 2026-10-03 по `developer.chrome.com/docs/android/intents` и
`add-event-to-calendar-docs/services/google.md`:

- Chrome на Android запускает внешнее приложение только по `intent:`-ссылке, только из
  действия человека и только `browsable`-экраны; у Google Календаря browsable — просмотр
  события. Значит нативное окно создания события с сайта открыть нельзя.
- Ссылка `calendar.google.com/calendar/render?action=TEMPLATE` — единственная, которая до
  сих пор доходит до веб-редактора на Android; на телефоне веб-версия выглядит мелко,
  уменьшить её сайт не может.
- Веб-редактор сохраняет событие в аккаунт браузера и в выбранный там календарь. Если это
  не тот аккаунт/календарь, что включён в приложении телефона, записи на телефоне не
  появится — это главная причина жалобы владельца 03.10.
- Файл `.ics` после скачивания открывается приложением календаря телефона: крупное окно,
  событие ложится в календарь телефона и сохраняет наши `VALARM`. Это единственный путь,
  дающий «окно как в приложении».

Реализация 0.4.5: `calendarAddTarget()` — на Android и в Chromium-браузерах собирает
`intent://…;#Intent;scheme=https;package=com.google.android.calendar;S.browser_fallback_url=…;end`
(браузер уходит на веб-форму, если приложение не отозвалось), иначе отдаёт веб-форму.
Ссылка открывается синхронно из обработчика нажатия. После сохранения — окно в приложении
с событием и двумя способами; в нём же сказано про аккаунт браузера.

## 0.4.7: iPhone — только файл, лишнего окна Google нет

Проверено владельцем 03.10.2026 на iPhone: событие, скачанное файлом .ics, сохраняется
в Календарь; уведомления о событии на сегодня приходят сразу после добавления.

Ограничение iOS (не обещать иное): сайт не может открыть окно создания в Календаре
Apple. iOS принимает событие либо файлом `.ics`, либо **подпиской на поток**
(«Подписной календарь»: Настройки → Приложения → Календарь → Учётные записи календаря →
Добавить → Другое → Подписной календарь). Поэтому на iPhone/iPad
`calendarAddTarget()` возвращает `kind: 'none'` — приложение ничего не открывает
автоматически, а окно после сохранения ведёт к файлу («Сохранить в Календарь iPhone»).
Кнопка Google остаётся вторым способом: она полезна, только если в браузере выполнен
вход в аккаунт Google.

`isIosClient()` учитывает iPadOS 13+, который представляется как «Macintosh» с
признаком «Mobile» в строке (у настоящего macOS его нет).

Подписка на поток (.ics по постоянной ссылке) — единственный «сам»-путь на iPhone и
единственный способ, при котором событие, созданное одним членом семьи, оказывается в
календаре другого без общих аккаунтов Google. Требуется постоянный адрес файла;
варианты хранения (публичная страница приложения против приватного календаря Google
через API) предложены владельцу — решения пока нет.

## 0.5.2: ГРАНИЦЫ НАДЁЖНОСТИ УВЕДОМЛЕНИЙ (ПРОВЕРЕНО ПО ДОКУМЕНТАЦИИ)

- GitHub Actions `schedule` — «по возможности»: задержки и пропуски запусков под нагрузкой,
  худшее время — начало часа (наш cron в рабочей ветке: `17,47 * * * *`).
  Источники: docs.github.com «Events that trigger workflows» (schedule), практика сообщества
  (dev.to «GitHub Actions Cron Was Late 30 Nights Straight, Then Skipped One», steadycron.com).
- Публичные репозитории: расписание **автоматически выключается после 60 дней без
  активности**; письмо автору — примерно за 23 дня; включение обратно — вручную.
- Расписания выполняются **только из ветки по умолчанию**. Следствие: пока `main` содержит
  старый отправитель, автоматические напоминания идут старой логикой.
- iPhone: web push — только для приложения, установленного на экран «Домой» (iOS 16.4+,
  разрешение из жеста). Фоновой синхронизации нет (Background Sync / Periodic Sync в iOS
  не поддержаны). Подписки iOS могут перестать работать без внятной ошибки (в отличие от
  Chrome, который отвечает 410 Gone).
- Поэтому в приложении предусмотрен догон: при открытии оно показывает напоминания,
  пропущенные при закрытом приложении (владелец наблюдал это 04.10.2026).

## 0.5.3: КАК ЧИТАТЬ СЧЁТЧИКИ В ОТЧЁТЕ УСТРОЙСТВА

- `webPush` — пишет Service Worker в обработчике `push`. Ноль при живой подписке значит:
  до устройства не дошёл ни один push (проверять отправителя и канал доставки iOS).
- `foreground` — напоминания, показанные приложением при открытии (догон пропущенного).
  Работает даже без push, но только когда приложение открыто.
- `background` — фоновая синхронизация: на iOS не поддерживается, там всегда 0.
- `calendarExport.eventCount` — сколько событий отдано в календарь; уведомление по ним
  показывает сама система (Google/Apple), независимо от push.

## 0.5.8: РУЧНОЙ ЗАПУСК, БУДИЛЬНИК, ПРИЗНАКИ В ОТЧЁТЕ

- **Ручной запуск «Push reminders»:** режим `reminders` (по умолчанию) — обычный цикл с
  дайджестом покупок; режим `test` — проверочный push, он открывает Настройки (это норма).
- **Будить отправителя:** приложение само просит GitHub запустить цикл сразу после своей
  записи. Требуется право **Actions: write** у токена на публичный репозиторий. Проверка в

- **Отчёт устройства:** `prefs.shoppingPush` — включён ли дайджест на этом устройстве;
  `webPush.receivedCount` — сколько push реально принято (на Android проверено).
- **Первый дайджест** смотрит на 24 часа назад: после включения тумблера не нужно ждать

## 0.5.9: ЧТО ДЕЛАТЬ, ЕСЛИ БУДИЛЬНИК НЕ СРАБОТАЛ

- В отчёте/журнале ищите запись `wake`. Коды: **403** — у токена нет права `Actions: write`
  на публичный репозиторий; **404** — токен вообще не видит этот репозиторий (типично для
  fine-grained токена, выданного только на приватное хранилище); `skipped` с причиной
  `offline`/`token`/`config` — попытки не было.
- Починка: открыть настройки токена (github.com → Settings → Developer settings), добавить
  публичный репозиторий в доступ и дать право **Actions: Read and write** (для классического
  токена — области `repo` и `workflow`). Значение токена при этом не меняется, в приложении
  ничего переставлять не нужно.
- Проверка без ожидания: Настройки → Уведомления → «Быстрый запуск уведомлений» →
